面向 OpenCode 的多代理研发编排插件

不要把 oh-my-openagent 理解成“更多 Agent”。它真正解决的是研发任务的计划、分工、执行与验证闭环。

这个页面帮助你系统理解 oh-my-openagent.json 的作用、各代理的岗位边界、不同使用模式的取舍，以及如何把它放进 Git Issue 驱动的自驾代码库流程里。

1核心入口：OpenCode 插件机制
4Plan 链路：Prometheus / Metis / Momus / Atlas
3三层架构：计划层 / 执行层 / 工人层
2关键抽象：Category 决定任务类型，Skill 注入专业能力

一、核心判断

先把概念钉死。不然你会被一堆代理名字绕进去。

oh-my-openagent 不是一个独立 IDE，也不是单纯的提示词包。
它是运行在 OpenCode 上的多模型、多代理编排 harness。OpenCode 提供终端/IDE/桌面里的代码执行环境、LSP、多会话等基础能力；oh-my-openagent 借助插件机制扩展出代理、任务路由、后台任务、技能、MCP、命令和 hooks。
对象真实含义你该怎么理解
OpenCode开源 AI coding agent执行环境。它负责让 AI 看代码、改代码、跑命令、接 LSP。
oh-my-openagent多模型 agent orchestration harness编排层。它把一个 coding agent 拆成一个有岗位分工的研发小队。
oh-my-openagent.json插件配置文件规则表。控制模型、代理、category、并发、权限、fallback、skills。
Agent岗位化角色不是越多越好。每个代理必须有清晰边界。
Category任务类型路由代理委派任务时不直接选模型，而是选任务类型。
Skill专业上下文 + 工具注入给代理临时加载某个场景的 SOP、MCP、操作方法。
真实建议：你学习这个插件，重点不要放在“有哪些神话代理”。重点要放在“一个研发任务从需求到代码提交，中间每个节点谁负责、谁不能越权、用什么证据判断完成”。

二、先建立系统模型

它的本质是把单一 Agent 的长任务压力拆掉：计划交给计划者，执行交给执行者，审查交给审查者，搜索交给搜索者。

输入

任务请求

来自用户、Git Issue、Bug、需求文档、UI 截图、测试失败日志。

判断

意图与复杂度

简单任务直接做；复杂任务走 ulw；精确任务走 @plan → /start-work。

路由

代理与 Category

Sisyphus 或 Atlas 把不同任务派给合适的代理或 category。

闭环

验证与沉淀

运行测试、检查实现、拆分提交、记录失败归因和项目上下文。

一句话模型

用户目标
  → 任务判断
  → 计划拆解
  → 计划审查
  → 分工执行
  → 测试验证
  → 原子提交
  → 经验沉淀

三、运行链路：三层架构

官方文档把它描述为通过计划与执行分离，把简单 AI agent 变成协调开发团队。

01User提出任务、Issue、Bug、改造目标。
02Prometheus访谈、澄清、生成计划。
03Metis / Momus找缺口、审计划、拒绝模糊任务。
04Atlas读取计划，拆分并调度执行。
05WorkersJunior / Oracle / Explore / Librarian 等执行专项任务。
06Verification测试、review-work、git-master、归档。
层级核心角色解决的问题失败时的典型表现
计划层Prometheus / Metis / Momus需求不清、边界不清、验收不清Agent 自己脑补业务逻辑，改了一堆不该改的文件。
执行层Atlas任务拆分、并行调度、状态连续性多任务互相踩踏，前一个结论没传给后一个执行者。
工人层Junior / Oracle / Explore / Librarian / Looker具体编码、代码库侦察、文档检索、架构咨询、视觉分析高级模型被浪费在 grep；低级模型被迫做架构判断。

四、代理分工：不要记名字，记岗位

代理不是“越多越智能”。代理的价值来自边界：谁负责判断，谁负责执行，谁只读，谁不能乱改。

Sisyphus
主协调者 / 默认入口

负责理解目标、规划方向、调用子代理、推动任务完成。

适合：大部分中等复杂任务、需要自动探索代码库的工作。

不要：让它无限自由地重构全项目。

Hephaestus
深度自主工程师

适合 GPT-native 的深推理、复杂架构、跨文件 debug。

适合：难以定位的 bug、复杂技术方案。

不要：拿它做简单 grep 或文案修补。

Prometheus
战略计划者

先问清楚问题，再生成详细计划。复杂任务动代码前应该先经过它。

适合：Git Issue 转执行计划、需求澄清、边界定义。

不要：让它直接写业务代码。

Atlas
执行调度器

读取 Prometheus 计划，分配给专门的执行者，并持续验证进度。

适合：/start-work 后的计划执行。

不要：让它重新发明计划。

Sisyphus-Junior
具体任务执行者

category 任务的实际执行者，不能继续无限转派，避免委派循环。

适合：单个明确子任务、局部改动。

不要：让它做架构裁决。

Oracle
只读架构顾问

只读咨询，适合架构风险、安全风险、多系统取舍。

适合：计划评审、方案取舍、复杂问题诊断。

不要：让它改文件。

Explore
代码库侦察员

快速搜索代码、发现模式、找相关文件。

适合：repo 初探、定位函数、找调用链。

不要：让它写复杂实现。

Librarian
资料研究员

查文档、查开源实现、查库 API 和最佳实践。

适合：技术栈文档、第三方库用法。

不要：用它代替本地代码理解。

Metis
Plan Consultant / 缺口分析顾问

计划定稿前找遗漏、歧义、隐藏前提和验收缺口。

适合：计划还没写死、你怀疑需求不完整时。

不要：把它当成最终审批者。

Momus
Plan Critic / 严格计划批评者

计划准备执行前做 gate，判断是否足够清晰、可验证、可交给 Atlas 执行。

适合：高风险任务开工前的最后审查。

不要：让它替 Prometheus 写完整计划。

五、Plan 系列代理：Prometheus / Metis / Momus / Atlas 不是同一种东西

你在输入 @plan 后看到 @Momus - Plan Critic 和 @Metis - Plan Consultant，不是因为它们是“计划模式”，而是因为它们是两个可直接唤起的计划质量控制代理。

一句话区别：
Prometheus 负责写计划，Metis 负责找计划缺口，Momus 负责严格审查计划能不能开工，Atlas 负责拿着通过审查的计划去执行。

为什么 @plan 下拉里会看到 Metis 和 Momus？

因为它们的展示名本身就属于计划链路：Metis - Plan Consultant、Momus - Plan Critic。这不是两种 plan 模式，而是两个不同 agent。官方和 GitHub issue 里都能看到这些显示名映射：prometheus 对应 Plan Builder，atlas 对应 Plan Executor，metis 对应 Plan Consultant，momus 对应 Plan Critic。

代理你可以怎么理解主要问题使用时机错误用法
Prometheus
Plan Builder		计划作者 / 需求访谈者这件事到底要怎么做？边界是什么？验收是什么？复杂任务动代码前；Git Issue 转实施计划。让它直接写业务代码，或者不看计划就执行。
Metis
Plan Consultant		计划顾问 / 缺口分析者这个计划漏了什么？哪里需要猜？哪里会导致 AI 自作主张？Prometheus 计划初稿出来后，或者你感觉需求还不完整时。把它当最终审批；让它替你决定业务取舍。
Momus
Plan Critic		计划批评者 / 开工 gate这个计划是否足够清晰、可执行、可验证？能不能交给 Atlas？计划准备进入 /start-work 前。没有计划就直接找 Momus；或者它说有 blocker 你还强行开工。
Atlas
Plan Executor		执行调度者如何按计划拆分任务、调度 worker、验证结果？/start-work 后执行已经通过 gate 的计划。让它重新发明计划，或者用它消化模糊需求。

更准确的计划链路

01@plan / Prometheus访谈、探索 repo、生成计划初稿。
02Metis找隐藏前提、歧义、遗漏验收、AI 可能脑补的地方。
03修订计划把 Metis 发现的问题补进计划，而不是直接跳过。
04Momus严格判断是否 READY_TO_EXECUTE。
05/start-work / Atlas按计划执行、分发子任务、持续验证。
06Verification测试、review、提交、沉淀。

Metis 和 Momus 的核心差异

Metis

计划还没定稿时用

它的价值是暴露“你以为清楚、其实不清楚”的地方。它偏顾问，偏补洞，偏前置发现问题。

@Metis Review this plan as a gap analyzer.
Focus on hidden assumptions, ambiguous requirements,
missing acceptance criteria, edge cases, and places
where implementation would require guessing.
Momus

计划准备执行前用

它的价值是挡住烂计划。它偏审判，偏 gate，偏判断是否能交给执行系统。

@Momus Review this plan as a strict execution gate.
Return READY_TO_EXECUTE or NEEDS_REVISION.
Check scope, affected files, executable tasks,
acceptance criteria, verification commands,
forbidden changes, and unresolved decisions.
真实建议：你做自驾代码库时，别把 Metis 和 Momus 当成“可选装饰”。只要任务涉及多文件、多模块、权限、数据结构、支付、账务、架构或重构，就应该让它们做计划 gate。否则你是在把模糊需求直接丢给执行 agent，让它用代码替你做产品决策。

六、oh-my-openagent.json 到底管什么？

你可以把它理解为“多代理研发系统的控制台”。但不要一上来乱改。先理解配置项背后的治理含义。

配置区域负责内容什么时候需要改
agents为具体代理设置模型、权限、prompt、fallback。某个代理效果长期不稳定，或者你要限制它的读写权限。
categories定义任务类型对应的模型、温度、工具、附加提示词。你要针对 UI、深推理、快修、文档写作做不同路由。
background_task控制后台任务并发、provider 并发、model 并发。出现限流、费用失控、并行任务互相抢资源。
sisyphus_agent控制主编排系统、Prometheus planner、默认 builder 替换。你想恢复原生 OpenCode，或者调整计划代理行为。
skills配置内置/自定义 skills，指定来源、启用、禁用、工具权限。你要给项目加入 git、playwright、设计走查、review 等专业 SOP。
team_mode实验性并行多代理团队模式。只有当普通编排跑稳后再考虑。默认不该打开。

一个更安全的基础配置思路

{
  "background_task": {
    "defaultConcurrency": 3,
    "providerConcurrency": {
      "openai": 2,
      "google": 3,
      "anthropic": 2
    }
  },
  "sisyphus_agent": {
    "disabled": false,
    "planner_enabled": true,
    "replace_plan": true
  },
  "skills": {
    "enable": ["git-master", "review-work", "frontend-ui-ux"],
    "disable": []
  }
}
现实建议：刚开始不要追求“最强配置”。先用默认配置跑固定任务集，记录失败类型，再改模型、权限、category。没有基线就调配置，本质是在蒙。

七、日常怎么用：三种模式

不同复杂度要走不同路径。最危险的用法是所有任务都一句话丢给 ulw。

简单任务：直接 prompt

适合拼写修复、单文件小改、明确 bug、小范围样式问题。

Fix the typo in the settings page title. Keep the change minimal.

判断标准：不需要探索大量上下文，不需要拆计划，不需要跨模块协调。

复杂但懒得解释：ulw / ultrawork

适合你知道目标，但不想详细解释项目结构，让它自己探索代码库、找模式、实现并验证。

ulw fix the failing tests and keep changes minimal

风险：它会更自主。适合实验，不适合高风险业务逻辑。

复杂且要求可控：@plan → /start-work

适合 Git Issue、跨文件功能、架构改造、支付/权限/数据迁移等高风险任务。

@plan "Implement issue #42. Inspect the codebase first. Define affected files, acceptance criteria, and verification commands. Do not edit code yet."

/start-work

这是你做自驾代码库时最应该采用的主流程。

八、命令体系：/ulw-loop 这一类指令不能漏

这里是我上一版漏掉的重点。ulw 是一种触发 ultrawork 的 prompt 前缀，而 /ulw-loop 是一个持续执行命令。两者都和“强自主执行”有关，但风险级别完全不同。

命令 / 写法核心作用适合场景主要风险
ulw ...用 ultrawork 模式处理当前任务。复杂但边界还算清楚的修复、探索、实现。会更主动探索，可能扩大范围。
/ralph-loop "..."启动自引用开发循环，持续推进直到完成信号或达到最大轮数。长任务、需要自动续跑、不想手动反复催促。完成检测依赖机制，失败时会浪费 token。
/ulw-loop "..."在 ultrawork 强度下启动 loop；并行代理、后台任务、激进探索都会更强。大型、多步骤、可接受高成本的自动执行。最容易失控：跑太久、越界改动、成本不可控。
/cancel-ralph取消 Ralph Loop。发现 loop 方向错了或已经失控。只能止损，不能替代前置计划。
/stop-continuation停止当前会话里的 continuation 机制，包括 Ralph Loop、todo continuation、boulder state。发现 agent 一直续跑、不停重复、后台任务卡住。可能中断未完成任务，需要人工检查状态。
/init-deep生成分层 AGENTS.md，让不同目录有自己的上下文。老项目、复杂项目、目录结构稳定的项目。生成后不维护，会变成过期上下文。
/refactor使用 LSP、AST-grep、架构分析和 TDD 验证做重构。命名迁移、模块重整、较系统的代码整理。不适合没有测试保护的核心业务逻辑大改。
/handoff生成当前工作上下文交接文档。任务未完成、准备换会话、需要让下一个 agent 接续。如果前面没有真实验证，handoff 只是漂亮总结。

/ulw-loop 和 ulw 的区别

ulw

一次强模式执行

更像是“这次回答请进入 ultrawork 模式”。它会更积极地探索、计划、调用子代理，但仍然是一次任务请求。

/ulw-loop

强模式 + 自动续跑

更像是“不要停，直到任务完成”。它会在 ultrawork 模式下持续推进，默认更适合大任务，但也更容易浪费成本。

/ralph-loop 和 /ulw-loop 的关系

/ralph-loop 是持续推进机制；/ulw-loop 是在这个持续推进机制上叠加 ultrawork 强度。官方文档对 /ulw-loop 的描述就是：和 ralph-loop 类似，但启用 ultrawork mode；这意味着并行代理、后台任务、激进探索都会更强。

现实判断：/ulw-loop 不是日常默认模式。它适合“你已经定义清楚目标、边界、验收标准、最大轮数、验证命令”的任务。否则它只是把不清楚的需求，用更高成本、更高自主性放大。

推荐用法

# 不推荐：目标过大，边界不清
/ulw-loop "make this project production ready"

# 推荐：目标、边界、验收和停止条件明确
/ulw-loop "Fix issue #42. Scope is limited to auth/session handling. Do not refactor unrelated modules. Run lint, typecheck, and auth tests. Stop only after verification passes or after reporting a blocker." --max-iterations=20

什么时候不要用 /ulw-loop

需求还没想清

先用 @plan，不要让 loop 替你猜业务逻辑。

没有测试保护

没有验证命令，loop 只能靠自我感觉完成。

高风险核心链路

支付、权限、数据迁移、账务逻辑，必须先计划审查再执行。

九、Category 与 Skill：这两个概念最容易混

Category 回答“这是什么类型的任务”；Skill 回答“这个任务需要哪套专业方法和工具”。

概念决定什么例子错误用法
Category模型、温度、思维方式、工具开关visual-engineering、deep、quick、writing把所有任务都塞进 deep，成本高且慢。
Skill专业上下文、流程、MCP、操作规范git-master、playwright、frontend-ui-ux、review-work做一个万能大 skill，把所有规则塞进去。

内置 Category 的学习重点

visual-engineering

前端 / UI / 样式 / 动效

适合移动端页面、组件、视觉修复、设计还原。

ultrabrain

极深推理

适合架构、复杂取舍、高风险技术判断。

deep

深度问题解决

适合一个清晰目标、一个明确交付物。不要塞多个目标。

quick

小任务快修

适合单文件、低风险、快速执行。

writing

文档写作

适合 README、技术说明、交付文档。

unspecified-high / low

兜底任务

当任务不属于明确类型时使用，但最好逐步沉淀成自定义 category。

面向你自驾代码库的 Skill 拆法

issue-intake          # 把 Git Issue 转成任务输入
plan-review           # 检查计划是否可执行、可验证
implementation-boundary # 限制改动范围、禁止无关重构
verification          # 定义 build/test/lint/手工 QA
failure-analysis      # 失败归因与下次避免
context-update        # 把经验沉淀进项目 harness
handoff               # 交付总结与人类审核信息

十、推荐工作流：放进 Git Issue 驱动研发

如果你的目标是“自驾代码库”，就不要把 Issue 直接丢给 Agent 开干。中间必须有计划和验证 gate。

01Issue Intake提取目标、边界、验收标准、风险。
02@planPrometheus 生成可执行计划。
03Plan GateMetis / Momus / Oracle 审查计划。
04/start-workAtlas 拆分并调度执行。
05Reviewreview-work 并行检查目标、质量、安全、QA、上下文。
06Commitgit-master 拆原子提交，沉淀经验。

适合你的判断公式

任务越复杂，越不能直接执行。
任务越高风险，越要先写验收标准。
代码库越老，越要先探索现有模式。
上下文越多，越要把计划和验证写进文件。
Agent 越自主，权限边界越要硬。

十一、可直接复制的实战模板

这些模板是给你日常启动任务用的。不要写“帮我优化一下”这种空话。

1. Git Issue 转计划

@plan "Analyze GitHub issue #XX and create an executable implementation plan.

Requirements:
1. Inspect the existing codebase before proposing changes.
2. Identify affected files and existing conventions.
3. Define clear acceptance criteria.
4. Define verification commands.
5. Explicitly list MUST DO and MUST NOT DO constraints.
6. Avoid unrelated refactoring.
7. If business logic is ambiguous, mark it as a blocker instead of guessing.

Do not edit code yet."

2. 计划审查

十二、常见误区

这里说难听点：很多人用不好，不是工具不行，而是把流程治理当成“多装几个代理”。

误区 1

所有任务都用 ultrawork

这等于把计划、判断、执行、验收全交给一个黑盒。小项目爽，大项目会乱。

误区 2

把所有代理都配最强模型

Explore 和 Librarian 做搜索，用最强模型是浪费。模型匹配岗位，不是堆成本。

误区 3

没有验收标准就开干

没有验收标准，Agent 会用“看起来完成”代替“真的完成”。

误区 4

只写提示词，不做权限约束

“不要乱改”不如配置权限、限定目录、限定工具。边界要靠系统，不靠自觉。

误区 5

计划评审只是走形式

Metis / Momus 的意义是挡住烂计划。你如果什么计划都放行，等于没有 gate。

误区 6

跳过失败归因

失败不沉淀，下一次还会失败。自驾代码库的核心不是一次跑通，而是越跑越稳。

十三、学习与验证清单

你要学会这个插件，不是靠看文档，而是靠跑固定任务集，看每个节点是否可靠。

安装验证
能运行 bunx oh-my-openagent doctor，确认系统、配置、工具、模型解析没有明显错误。
代理可见性
确认 Sisyphus、Prometheus、Atlas、Oracle 等代理在 OpenCode 里可见或可调用。
计划质量
Prometheus 生成的计划是否包含目标、范围、受影响文件、验收标准、验证命令、风险。
计划 Gate
Metis / Momus / Oracle 是否能发现计划里的模糊点、隐藏前提、无验证项。
执行边界
Atlas / Junior 是否按计划执行，是否避免无关重构和扩大范围。
验证证据
完成后是否真的跑了 build/test/lint/手工 QA，而不是口头说完成。
提交质量
git-master 是否能拆出原子提交，每个提交是否目的清晰。
经验沉淀
失败原因、项目规则、踩坑点是否沉淀进项目 harness，而不是下一次重犯。

建议准备 10 个固定测试任务

任务类型测试目的重点观察
小修复验证 quick 路由和最小 diff是否只改必要位置。
单文件功能验证简单实现能力是否理解现有代码风格。
多文件功能验证计划与执行协同是否先找影响范围，再动代码。
UI 任务验证 visual-engineering / frontend-ui-ux是否尊重设计细节和移动端约束。
测试补充验证测试意识是否只写表面测试，还是覆盖关键路径。
失败恢复验证 debug 和复盘失败后是否归因，而不是盲改。
文档任务验证 writing category是否写出可执行文档，而非泛泛说明。
原子提交验证 git-master是否把不相关变更拆开。
计划审查验证 Metis / Momus能否拦住模糊需求。
上下文沉淀验证 harness 更新是否把经验变成下次可复用规则。
